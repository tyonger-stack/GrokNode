# 市场首页图标资产 —— 要求 1「图标一致」此前从未被测过（2026-10-05 18:0x）

> 要求 1 明写「顺序、数量、**图标**、名称、分类标签等所有视觉能看到的均一致」。
> 但 `scripts/verify-marketplace-parity.mjs` 的实机逐区块对拍**只比行名**
> （`officialSections[t].names.join("|")`）—— 图标从来没进过任何机器比对。
> 本文档补上这一维，结论是：**图标不一致，且不是「同一份图不同交付方式」。**

## 一、交付方式不同

| | 官方 0.66 | 本地 |
| --- | --- | --- |
| 引用方式 | **data URI 内联** | **远端 URL** |
| 媒体类型 | PNG 与 SVG 混合 | PNG（`cursor-cdn.com` / `ptht05hbb1ssoooe.public.blob.vercel-storage.com`） |
| 官方内联样本 | `data:image/png;base64,iVBORw0KGgo…`（`iVBORw0KGgo` 即 PNG 魔数） | — |
| 本地样本 | — | `https://cursor-cdn.com/plugin-logos/production/0df2f63c7ffbd16f.png` |

⚠️ 一次读数纠错：我第一版按 `/` 切 data URI 的尾部来判类型，把官方报成「内联 SVG」
（`image/svg+xml` 里有 `/`，切出来是 `xml;base64,…ASUVORK5CYII=`，尾巴恰好像 SVG 的 `</svg>`）。
按前缀判才是准的：**官方 PNG 与 SVG 混合，本地全是远端 URL**。

## 二、尺寸不同 —— 这不是「同一张图」

两套读数，**依据不同，不要混用**：

**A. 离线解字节（`cmp-icons.mjs`）** —— 官方 data URI 解 base64，远端 URL 走 HTTP 取回，
各自读 PNG 头：

```
按「区块|行名」对齐 39 条
  官方内联尺寸几乎一律 112×112（少数 67×67 / 112×110）
  本地远端尺寸五花八门：400×400 / 1024×1024 / 621×621 / 512×511 / 294×290 /
                      250×250 / 200×200 / 135×133 / 67×67 …
  尺寸相同的：1 条（效率|Atlassian，67×67）
  字节 sha256 相同：1 / 40；不同：38 / 40
```

**B. parity 的 DOM 读数**（`verify-marketplace-parity.mjs`，页面里 `img.naturalWidth`）：

```
可比对 40 行；交付方式不同 39 行；
两侧都解析出 <img> 后固有尺寸不同的 12 行，
另有 28 行至少一侧未解析出图标（该数是下界，不是全量）
```

B 的 12 是**下界**：只有两侧都定位到 `<img>` 的行才进入尺寸比较，另外 28 行被计入
「未解析」。**不要把 12 当成「只有 12 行不同」** —— A 的离线字节比对给出的是 38。

而且官方那份**系统性地小得多**，说明是**重新下采样**过的资产，不是原图：

| 行 | 官方内联 | 本地远端 |
| --- | --- | --- |
| 设计 \| Canva | 16,916 B / 112×112 | 145,465 B / 512×511 |
| 财务 \| Aave | 7,433 B / 112×112 | 79,969 B / — |
| 代码 \| Appwrite | 15,505 B / 112×112 | 174,325 B / — |
| 数据 \| Astronomer | 7,977 B / 112×112 | 132,586 B / — |
| 精选插件 \| Granola | 10,257 B / 112×112 | 59,481 B / 1024×1024 |

**统一到 112×112 是一个有意的服务端归一化**：logo 在画布里的相对占比被重新对齐过。
本地直接引用原始素材，同一个 logo 在不同品牌下**占框比例不一致**（有的四周留白多、
有的几乎贴边）。

两侧的**渲染盒相同**：实测两侧行图标 `getBoundingClientRect()` 均为 `39×39`
（官方 14 个区块、本地 13 个区块抽样一致）。所以差异不在盒子大小，在**资产本身**。

## 三、对要求 1 的影响

要求 1 的「图标一致」**不成立**。已确证的部分：

1. 引用方式不同（内联 vs 远端）—— 影响首屏可达性：本地图标依赖两个外部 CDN，
   任一不可达即显示空框；官方内联则**无外部依赖**。
2. 资产不同（离线字节比对 38/40 不同、38/39 尺寸不同）—— 影响视觉一致性。

**2026-10-05 22:0x 复核，这两条都已经不需要截图来回答了**：
1. D18 落地后 parity 实测「两侧都解析出 `<img>` 后固有尺寸不同的 **0 行**」—— 官方内联归一化到
   112×112、本地同步走宿主缩放，**资产层面的尺寸差已被测量消掉**，不再是推断。
2. 截图对拍在本地环境**确认不可得**，原因已查明（不再是「卡在导航循环里」这种含糊说法）：
   `Page.captureScreenshot` 在官方那个 Electron 页面上**四种参数组合全部超时**（原生长度、
   Emulation 1180×1000、Emulation+clip+captureBeyondViewport、清除 Emulation 之后），
   `Page.startScreencast` 能启动但 **0 帧**；同一时刻本地 app 的 screencast 正常出 3 帧
   （1728×1019）。桌面级 AX 截图同样返回 `screenshot: none`。
   ⇒ **官方窗口不产合成帧**，这是环境限制，不是脚本 bug。改用 Accessibility 树取证，
   它给出有序、精确、含行尾控件状态的等价结构证据，已落
   `docs/evidence/marketplace-parity-20261005/homepage-row-diff.json`（两侧判据互相独立）。

## 四、检测器自身踩过的三个坑（值这一节本身）

把「行图标」加进 parity 时，定位器连错三次，而且**两次都是静默错**：

| 版本 | 做法 | 症状 |
| --- | --- | --- |
| v1 | `closest("li")` 或回退一层 `parentElement` | 40 行里 28 行读成「无图标」→ **少计**，报 12 |
| v2 | 向上走到任意含 `<img>` 的祖先 | 自己没图标的行（`oh-my-claudecode`、`1Password`）**捡到邻行的图** → **错归属**，报 13 且样例里出现本该无图标的行 |
| v3 | 接受祖先的条件：含 1 个 `<img>` **且**只含 1 个 `row__name`；超过 1 个图即判定已出该行 | 归属正确 |

第三版之后仍只报 12，因为 28 行**确实没能两侧都解析出图标**。此时正确的做法是
**把分母一起报出来**（`另有 28 行至少一侧未解析出图标（该数是下界，不是全量）`），
而不是继续调参把数字凑好看。

**少计的检查比没有检查更糟**：它输出一个像测量值的数字。v1 报的「12」看起来精确，
实际上是 38 的一部分 —— 和本项目之前记的「恒假的检查」同一个病根，只是方向相反。

## 六、怎么改（**本轮未执行**）

要对齐官方，本地不能继续直接透传 catalog 里的 `iconUrl`，需要在渲染前做
「取远端图 → 归一化到 112×112 → 按官方那份内联」的处理。这不是纯 UI 问题：
它取决于服务端是否提供 112×112 变体。**先要确认官方那批 112×112 是从哪来的**
（同一 CDN 的尺寸参数？还是服务端预生成的字段？），否则「怎么改」就是臆造。

**不做也不会更糟**：现状已经能用，只是图标的相对大小与官方不一致。

## 七、教训

- **要求里逐项列出的东西，必须逐项有机器比对，否则等于没做。**
  「顺序、数量、图标、名称、分类标签」五项里，长期只有后两项进了 parity。
- **「同一份图的不同交付方式」和「不同的图」在页面上看起来可能很像** ——
  必须解字节、读尺寸头，不能靠「都显示了一个 logo」判断。
- **按 `/` 切 URL 尾部来判 media type 是错的**（`data:image/svg+xml` 里含 `/`）。
  判类型要看 `data:` 之后、分号之前的那个字段。
- **检测器报出的每个数都要能被单独证伪**。写完先在真实数据上确认它报出**你预期的那一侧**，
  再拿已知的反例（无图标的行）确认它**不**报。
